# 乐队管理系统（Band Hub）架构设计与对抗性审查

> 版本 v1.0 · 2026-08-17 · 本文是系统的「宪法」，所有结构变更先回到本文档的公理校验。

---

## 1. 问题定义

现状：四件工具分散在四个载体上——

| 工具 | 载体 | 管什么 | 核心问题 |
|---|---|---|---|
| 歌单 + 排练/演出通告 | Excel | 曲目 + 日程 | **资产与流程混装**，文件越用越乱 |
| 乐队介绍 | 微信笔记 | 对外形象 | **平台锁定**：不可版本化、链接不稳、无法被统一入口引用 |
| 演出风控速查表 | HTML | 演出准备 | 独立漂浮，调取靠翻聊天记录 |
| 演出复盘表单 | PDF | 经验沉淀 | 填完之后**没有归档目的地**，回路漏电 |

目标：统一入口、模块独立、入口纯净、可复制、可迭代、有门槛。

---

## 2. 第一性原理拆解：乐队管理系统在管理什么？

剥掉所有工具形态，一个乐队运转只需要处理**三类信息**：

| 类别 | 定义 | 特征 | 本系统对应 |
|---|---|---|---|
| **资产（Asset）** | 随时间增值、低频修改、丢失代价高 | 越攒越值钱 | 曲库、乐队介绍、风控知识库、复盘档案 |
| **流程（Flow）** | 高频变更、短生命周期、过期即废弃 | 用完即走 | 排练/演出通告、待办协调 |
| **回路（Loop）** | 让系统随时间变强的机制 | 周期性触发 | 复盘 → 沉淀进风控速查/曲库状态 → 下一场更好 |

**关键诊断：现有系统是按「文件格式」组织的（Excel/HTML/PDF/微信笔记），而不是按「信息的生命周期」组织的。** 这就是为什么歌单（资产）和通告（流程）会挤在同一个 Excel 里——不是你不会分类，是分类维度从一开始就错了。

由此推导：**系统结构必须按生命周期分层，而不是按工具格式分层。**

---

## 3. 六条架构公理

所有设计和后续迭代，用这六条校验，违反任何一条的提案默认否决：

| # | 公理 | 一句话理由 |
|---|---|---|
| A1 | **单一入口** | 所有模块从入口 ≤2 次点击可达；入口是系统里唯一的「公共记忆点」 |
| A2 | **模块自包含** | 一个模块 = 一个文件夹，无交叉引用；删掉任一文件夹，其余部分照常工作 |
| A3 | **入口极简** | 入口只做导航，零数据、零公告、零业务逻辑；「不展示无关信息」必须是**结构保证**，不靠人的纪律 |
| A4 | **资产/流程分离** | 资产与流程永不共存于同一文件（这是对现有 Excel 的结构性纠错） |
| A5 | **自有格式** | 一切内容以自持有格式（HTML/XLSX/PDF/MD）存储；第三方平台（微信等）只做**分发出口**，永不做存储 |
| A6 | **沉淀有回路** | 每个流程产物都有唯一归档目的地；复盘表单必须在生成时就写明归档路径 |

## 4. Hub-and-Spoke 架构

```
band-hub/
├── index.html                  ← 唯一入口（纯导航，<15KB，可随时重建）
├── README.md                   ← 系统说明书（操作手册/部署/复制协议）
├── docs/
│   └── architecture.md         ← 本文档
├── assets/                     ← 共享视觉资源（logo/海报，只放静态素材）
├── modules/                    ← 模块层：五件套，互相独立
│   ├── songs/    曲库.xlsx      资产·对内   乐队曲目总台账
│   ├── schedule/ 通告.xlsx      流程·对内   排练/演出通告流水
│   ├── intro/    index.html    资产·对外   乐队介绍（原微信笔记）
│   ├── risk/     index.html    资产·对内   演出风控与准备速查
│   └── review/   index.html    回路·对内   复盘表单下载 + 归档索引
│       └── archive/            复盘扫描件归档（按场归档，只增不改）
```

**模块五件套与三类的映射：**

| 模块 | 层级 | 变更频率 | 载体 | 谁来更新 |
|---|---|---|---|---|
| 曲库 | 资产·对内 | 周/月 | XLSX | 曲库负责人 |
| 通告 | 流程·对内 | 每周 | XLSX | 通告发起人 |
| 介绍 | 资产·对外 | 月/季 | HTML | 对外负责人 |
| 风控 | 资产·对内 | 每次复盘后 | HTML | 复盘执行人 |
| 复盘 | 回路·对内 | 每场演出后 | PDF+HTML | 当场带队人 |

**部署双轨：**
- 本地：双击 `index.html` 即用，全部相对路径，无任何外部依赖，**离线可用**（演出现场无网是常态）
- 线上：推到 GitHub Pages，得到一个固定 URL，发乐队群即可（手机/微信内打开均正常）

## 5. 对抗性审查（红队 10 项）

对架构逐项攻击，每项给出可执行的缓解措施：

| # | 攻击向量 | 攻击场景 | 缓解措施（已落实到结构） |
|---|---|---|---|
| R1 | 入口单点故障 | index.html 被误删/损坏，全队「失联」 | 入口纯静态极简，可 5 分钟重建；模块按文件夹名可直接访问；README 附重建说明 |
| R2 | 数据单点故障 | XLSX 被误操作覆盖，曲库资产蒸发 | git 版本化（见 README 备份协议）+「大改前另存带日期副本」纪律 |
| R3 | 平台锁定复发 | 成员图省事，新内容又放回微信笔记 | 公理 A5 写进 README 违禁清单；微信只转发入口 URL，本体永远在系统内 |
| R4 | 权限混层 | 介绍页对外、复盘对内，同一 URL 树泄露内部信息 | 目录已按敏感度标注对内/对外；部署可拆「公开版（只含 intro）/完整版（私库或本地）」两档 |
| R5 | 入口腐化（最可能的慢性病） | 今天加公告、明天加看板、后天加闲聊，入口变垃圾场 | 公理 A3 结构化禁止：想加任何功能 → 新建模块 → 入口只多一个链接；违禁清单见 README |
| R6 | 隐性耦合 | 为视觉统一共享 CSS/字体文件，改一处全站崩 | 刻意反 DRY：**每模块样式内联自包含，复制优先于复用**；视觉一致靠规范文档约束，不靠共享代码（规模小、维护者非工程师，独立性的价值 > DRY） |
| R7 | 更新断崖 | 非技术成员不敢碰 HTML | 每个模块 HTML 顶部集中「✏️ 可编辑区」，改文字不碰样式；日常高频操作全部落在 XLSX（全员都会用） |
| R8 | 规模衰减 | 复盘积累 100 场后无法检索 | archive/ 命名协议 `YYYY-MM-DD_场地_类型`；review/index.html 维护归档索引表（v1.2 升级为索引页自动生成） |
| R9 | 复制泄密 | 把系统复制给别的乐队时带上本队数据/复盘 | README「复制 checklist」逐项列出必清空文件 |
| R10 | 过度工程（元对抗） | 每周排练一次的乐队，配这么套系统是否过重？ | 核算运行成本：日常动作仅 2 个——发通告=XLSX 加一行；演出后=打印表单填完拍照归档。**结构复杂度一次性支付，运行复杂度趋近于零**；若乐队规模未到，砍掉 risk/review 两模块不影响核心三件套 |

## 6. 需求冲突主动检查（实现前审查）

你的原始需求里存在三处内在张力，逐个拆解：

| 冲突 | 张力 | 裁决 |
|---|---|---|
| 「入口纯净」 vs 未来想看统计/进度/看板 | 看板一旦进入口，入口就开始腐化（R5） | 统计永远是**新模块**（如 modules/stats/），入口只加一个链接，入口本身保持零数据 |
| 「互相独立」 vs 「视觉统一」 | 共享样式=耦合（R6） | 视觉规范文档对齐 + 代码各自内联复制；接受未来改风格要改多处的代价，换取单模块可随意重构的自由 |
| 「高效调取」 vs 「离线可用」 | 云端依赖 vs 演出现场无网 | 纯静态双轨：本地文件夹常备 + GitHub Pages 镜像；所有文件零外部依赖（无 CDN 字体/脚本） |

**与 BandManager（React 应用）的关系：** BandManager 是「一个模块」，不是「入口」。它保持独立部署（GitHub Pages），在入口里作为一个外链卡片存在。**永远不要把入口职责合并进 React 应用**——否则应用的任何 bug 都会让全队失联，直接违反公理 A2/A3。

## 7. 护城河分析：「有门槛」的本质

代码零门槛（静态页面谁都抄得走），门槛必须长在别处：

```
护城河 = 数据资产 × 使用回路 × 复制协议
```

1. **数据资产**：标注完整的曲库、逐场复盘档案、实战沉淀的风控案例库——抄走结构抄不走数据
2. **使用回路**：每次排练/演出都跑一遍「通告 → 执行 → 复盘 → 沉淀」，数据复利式增厚；对手拿到模板也只是空壳
3. **复制协议**：README 的复制 checklist 让系统能「出厂化」给其他乐队——出厂的只有结构，数据护城河永远留在本队

**结论：本系统的竞争力不在代码，在「每场演出都让它变厚一点」的回路设计。**

## 10. 观察清单（v1.3 建档 · 等真实使用数据裁决）

> 原则：以下都是"看起来是问题、但可能用起来根本不疼"的候选项。**禁止纸面预判提前动手**——跑过 2~3 场真实演出后，凭实际体验回来裁决。

**设计基准（v1.4 确认）：当前按「B 假设」设计——实际主动使用者 = 青宝 + 1~2 名核心搭档。**
内容密度不砍（B 规模消化得起），只为搭档加"角色直达"（手册锚点导航、复盘分工建议）。B→C 的迁移杠杆**不在把工具做得更好用，而在"价值可见化"**：复盘报告发群、歌单优化生效被全队看见——同伴在用、产出可见，才会带动第 4、5 个人。

| # | 观察点 | 裁决触发条件 | 候选动作 |
|---|---|---|---|
| O1 | 歌单双头维护：通告.xlsx 曲目安排 vs 演出手册「歌单一览」同一信息填两处 | 出现过"改一处忘另一处" | 合并为单一填写源，或手册歌单表改为"打印通告时一起打" |
| O2 | 归档三步摩擦：生成报告→存PDF→传archive→改索引，每场 3 次手动 GitHub 操作 | 月归档 >2 场且开始嫌烦 | 索引表改 localStorage 自动记录（代价：换设备不同步） |
| O3 | 专业版速查表使用频率 | 3 个月内无人打开 | 移入 docs/ 归档，入口卡片去掉该子链接 |
| O4 | 队员引导是否足够：入口一句话 + 页脚提示 | 有队员首次使用后问"怎么用" | 增加一页式使用说明（新模块，入口只加链接） |
| O5 | assets/ 空位 | 乐队 logo / 海报素材到位 | 启用并接入介绍页 |
| O6 | B→C 采纳信号：是否有第 4 名队员主动使用（不是被点名才用） | 2~3 个月内出现 ≥1 人 | 启动 C 化设计：任务化极简视图（每次打开只见"今天你该做的 3 件事"）；若 3 个月无人跟进，确认 B 为终态，停止投入 |
| O7 | 财务"导出→WPS另存→传云端"三步摩擦 | 月度记账嫌烦，或出现"只在 HTML 记、从不导 Excel"导致 Excel 与线上分叉 | 若摩擦成为阻碍：改为"HTML 页直传 GitHub API"（牺牲 file:// 离线，换一键发布），或接受 HTML 即权威、Excel 仅备份 |
| O8 | 分账规则（净结余按出勤均分 + 基金事件性凑款）是否被执行 | 出现"按比例抽成"回潮或分账争议 | 修订规则并更新财务页说明 |
| O9 | 通告双轨：速填器管创建分发 vs Excel 台账管长期归档，两套是否出现分叉 | ✅ v1.8 已结构性解决：速填器「确认发布」自动写 noticeLog → 通告记录页跨场汇总，"速填器即记录"；Excel 台账降级为可选深度归档。残余观察：通告记录存发布人本机 localStorage，多设备/换设备需手动导出导入——若发现记录经常丢失或从不同步，考虑迁到 GitHub API 存储 | 曲库扩充后仍需找 AI 更新速填器 DATA 块，否则新歌不可勾选（依赖提醒，非自动） |
| O10 | 排练合格线是否被执行（连续2遍无结构性失误才算会上）；教训库是否持续录入 | 攒 3 场复盘后教训库仍为空，或曲目型教训连续 3 场同类再现 | 若无人执行：把合格线压缩成速填器发排练通告时的固定文案；若同类曲目失误再现：该歌降级"排练中"禁上商演，直至复验通过 |
| O11 | 沉淀清单"复制→粘贴导入"两步摩擦（复盘系统→教训库跨文件数据流） | 攒 3 场后教训库条目 < 复盘报告沉淀段条目的一半 | 教训库改为读同一 localStorage 键（同源 GitHub Pages 下可共享，file:// 不行）；或接受由 AI 在收到复盘 PDF 时代录入 |
